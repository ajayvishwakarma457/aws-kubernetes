🌐 Networking & Ingress in Kubernetes

1. Networking Basics
    In Kubernetes, every Pod gets its own IP address. To let Pods talk to each other or the outside world, K8s provides:
      Pod-to-Pod → direct communication inside the cluster.
      Service → stable virtual IP (ClusterIP, NodePort, LoadBalancer).
          ClusterIP → internal only (default).
          NodePort → exposes on every node’s IP at a fixed port.
          LoadBalancer → integrates with cloud load balancer (AWS ELB, GCP LB).


================================================================================================================================================================

2. Ingress (smart router for HTTP/HTTPS)

    Instead of exposing each Service separately, Ingress lets you route external traffic into the cluster.
        Acts like an entry point / reverse proxy.
        Needs an Ingress Controller (e.g., NGINX, Traefik).
        Can handle:
            Path-based routing → /api → Service A, /shop → Service B
            Host-based routing → api.example.com → Service A, web.example.com → Service B
            SSL/TLS termination (HTTPS).



================================================================================================================================================================

3. Example Ingress YAML

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-ingress
  annotations:
    kubernetes.io/ingress.class: nginx
spec:
  rules:
  - host: demo.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /web
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80


👉 Now:
http://demo.example.com/api → goes to api-service
http://demo.example.com/web → goes to web-service

✅ Summary
  Networking ensures Pods, Services, and external clients can talk.
  Ingress = smart HTTP(S) entry point that routes traffic to the right Service.

1.png Diagram Explanation

    1. Networking & Ingress Flow
        User (outside the cluster)
            A client/browser makes a request to your Kubernetes cluster (e.g., http://demo.example.com/api).

    2. Ingress (entry point)
        The Ingress Controller (like NGINX Ingress) receives that request.

    3. Routing
        If the request path is /api → forward to Service A.
        If the request path is /web → forward to Service B.

    4. Service (inside cluster)
        A Service is a stable virtual IP that load-balances traffic to the right Pods.
        Example: api-service sends traffic to all Pods labeled app=api.

    5. Pods
        These are your app containers actually running the code.
        Services distribute traffic across multiple Pods to ensure high availability.


✅ So the flow is:
    User → Ingress → Service → Pods
    This way, you don’t expose Pods directly. You only expose an Ingress, which is easier to secure, manage, and scale.
